# Полнота и детальность метаданных

Описание набора — это то, по чему его находят и решают, можно ли им пользоваться. Две разные вещи часто смешивают.

**Полнота** — какая доля нужных полей заполнена. **Детальность** — насколько подробна сама схема: только название и описание или ещё период, территория, методика, список полей таблицы.

Платформа может быть подробной и при этом пустой: двадцать обязательных полей, в которых стоит прочерк. И наоборот: короткая схема, заполненная честно, полезнее длинной анкеты.

## Три уровня описания

Минимум, без которого набор нельзя использовать:

- название и описание человеческим языком;
- кто опубликовал и как с ним связаться;
- лицензия;
- дата последнего обновления;
- постоянный адрес.

Этого хватает, чтобы найти набор и понять, можно ли его брать.

Рекомендуемый уровень добавляет то, без чего набор трудно отфильтровать и трудно обновлять:

- охват по времени и территории;
- как часто обновляется;
- тема из общего справочника;
- формат и размер файла;
- язык.

Предметный уровень нужен там, где без него данные нельзя интерпретировать:

- статистика — методика, единица измерения, разрывы ряда;
- геоданные — система координат, масштаб, тип объекта;
- наука — авторы, финансирование, связь со статьёй;
- таблица — словарь полей: что означает колонка, какой у неё тип.

Словарь полей — это метаданные уже не о наборе, а о его содержимом. Для таблиц его описывают схемами вроде Frictionless Table Schema или CSV on the Web.

## Когда подробность вредна

Обязательная схема из пятидесяти полей замедляет публикацию. Поля начинают заполнять формально: копируют описание из соседнего набора, ставят сегодняшнюю дату в «период данных». Лучше короткая обязательная схема и необязательные предметные поля, чем длинная анкета, которую никто не читает.

Свои поля нужны, если отраслевой справочник или закон требует реквизита, которого нет в стандартной схеме. Они не нужны, если хочется «на всякий случай» сохранить внутренний номер из учётной системы.

## Как это сделано в платформах

Пометки — ядро, расширение, нет, не проверено, как в [сводной таблице](../12-appendices/03-platform-tables.md).

| Платформа | Своя схема полей | Что важно знать |
|-----------|------------------|-----------------|
| CKAN | расширение [ckanext-scheming](https://github.com/ckan/ckanext-scheming) | схема задаётся файлом. Кто ведёт расширение и какие версии ядра названы — в главе [про CKAN](../05-platforms/03-ckan-and-extensions.md). Несколько языков — расширение ckanext-fluent |
| Dataverse | в ядре | готовые блоки (цитирование, геоданные, социальные науки) и свои блоки |
| InvenioRDM | в ядре | основа — схема DataCite, дополнительные поля настраиваются |
| GeoNetwork | расширение (плагины схем) | профили ISO подключаются плагинами, не голым ядром |
| OpenDataSoft, Socrata, ArcGIS Hub | нет | несколько дополнительных полей бывают, произвольной схемы нет |
| Статический сайт | нет | схему пишет автор шаблона; готовой проверки полей нет |

Гибкая схема почти всегда означает сопровождение: кто-то должен решить, какое поле обязательно, и не дать схеме расползтись.

## Как проверить живой портал

1. Откройте десять случайных наборов, не самые свежие.
2. Для каждого отметьте, заполнены ли лицензия, издатель, дата обновления, период и территория.
3. Посмотрите, есть ли словарь полей у табличного набора.
4. Если портал отдаёт DCAT-AP, прогоните выгрузку через валидатор. На европейском портале данных для этого есть оценка качества метаданных (MQA): она считает заполненность, а не «красоту» текста.

Доля заполненных полей важнее длины формы. Портал, где лицензия есть у каждого набора, полезнее портала с тридцатью пустыми полями.
