# API и массовая выгрузка

Человеку достаточно сайта. Программе нужен устойчивый способ спросить каталог: какие есть наборы, что в описании, где файл. Это и есть программный интерфейс, API.

Без него каталог виден только тем, кто открыл сайт в браузере. Вышестоящий портал, поисковик и сервис на этих данных остаются за бортом.

## Четыре разные задачи

Их часто называют одним словом «API», хотя это разные возможности.

1. **Найти и прочитать описание.** Поиск по тексту и фильтрам, карточка одного набора. Пример — Action API у CKAN.
2. **Забрать все описания сразу.** Один файл или протокол, который отдаёт каталог целиком: `data.json`, RDF-выгрузка, OAI-PMH, карта сайта sitemap. Это нужно сборщикам. Поиск по одной странице результатов для них недостаточен.
3. **Получить сами данные.** Ссылка на файл, запрос к таблице, картографический сервис, статистический API.
4. **Узнать, что изменилось.** Лента RSS или выборка «изменено после даты», чтобы не скачивать каталог заново каждый день.

## Когда что нужно

Выгрузка всех описаний нужна почти всегда. Это минимум, по которому каталог могут собрать другие.

API поиска нужен, когда наборов сотни и больше или когда каталог входит в федерацию. Для двадцати наборов на статическом сайте хватает одного файла описаний и sitemap.

API к содержимому таблиц нужен, когда данные большие или обновляются часто и скачивать весь файл неудобно. Для архива годового отчёта достаточно файла.

Уведомления об изменениях нужны сборщикам больших каталогов. Маленькому порталу достаточно даты изменения в выгрузке.

Метаданные должны читаться без регистрации и без капчи. Иначе автоматический сбор либо невозможен, либо ломается при каждом обновлении защиты.

## Массовая выгрузка — не роскошь

Если данные можно получить только запросами к API, каждый, кому нужна вся база, выкачивает её по кусочку. Это долго для пользователя и дорого для сервера. Цифры показывают, насколько это лишнее. Европейский центральный банк отдаёт все ряды массовой выгрузкой: 108 файлов CSV на 93 ГБ, которые после перевода в Parquet занимают 664 МБ. У Всемирного банка в 2025 году такой выгрузки для показателей почти не было: 12% показателей, скачанных через API, — 3382 файла JSON на 22 ГБ, а в Parquet те же данные заняли 44 МБ. Довод «данные слишком большие, поэтому только API» обычно значит, что их не пробовали сжать.

Ограничения API разумны, только если рядом есть полная выгрузка. Zenodo в 2024 году ограничил выдачу одного поискового запроса десятью тысячами записей, а полной выгрузки описаний у него нет. Для портала, где наборов данных сотни тысяч, это заметное снижение открытости. Хорошие образцы обратного: Сенат Франции выкладывает свои базы целиком дампами SQL, российский адресный реестр ФИАС публикует полные выгрузки и отдельные файлы изменений.

## Неявные интерфейсы

Многие сайты отдают данные программам, даже если владелец об этом не написал. Причин три. API задумали, но не задокументировали. Сайт сам устроен как страница, которая получает данные скриптом из API, и этот API можно вызвать напрямую. Или API есть у платформы по умолчанию, а владелец о нём не знает: у WordPress это `/wp-json/`, у научных репозиториев DSpace — REST API и OAI-PMH, у серверов ArcGIS — ответ в JSON на любой адрес с параметром `?f=json`, у каталогов на Blacklight — тот же адрес с заголовком `Accept: application/json`.

Для пользователя такой интерфейс — находка: иногда это единственный способ получить данные с геопортала или из реестра. Для владельца — повод задокументировать то, что уже есть. Опираться на недокументированный интерфейс в постоянной работе рискованно: при обновлении сайта он меняется без предупреждения.

## Данные без прямой ссылки

Каталог, привыкший к модели «набор — это файлы по ссылкам», встречает и другие способы доступа.

- **Облачные каталоги.** Каталог Microsoft Planetary Computer отдаёт часть данных ссылками вида `abfs://…` во внутреннее хранилище Azure, реестр открытых данных Amazon — адресами бакетов S3, каталог Google Earth Engine — фрагментом кода для своей платформы. Данные открыты, но удобнее всего ими пользоваться внутри облака владельца.
- **«Сначала код» в машинном обучении.** Kaggle, Hugging Face, каталоги TensorFlow и PyTorch вместо ссылки на файл показывают строку кода, которая загружает набор библиотекой. Для специалиста это удобно, для общего поисковика данных — набор без файлов.
- **Только по запросу.** Часть статистических порталов отдаёт таблицу только в ответ на POST-запрос с выбранными параметрами, без постоянного адреса.

Если вы публикуете так, дайте рядом хотя бы одну обычную ссылку на файл или выгрузку: её поймут и человек, и сборщик, и архив.

## Как это сделано в платформах

Пометки — ядро, расширение, нет, не проверено, как в [сводной таблице](../12-appendices/03-platform-tables.md).

| Платформа | Поиск описаний | Все описания сразу | Данные |
|-----------|----------------|--------------------|--------|
| CKAN | ядро (Action API) | расширение (ckanext-dcat) | ядро (файлы и DataStore); заливка CSV — расширение XLoader |
| Dataverse | ядро | ядро (выгрузка метаданных и OAI-PMH) | ядро |
| InvenioRDM, DSpace | ядро | ядро (OAI-PMH) | ядро |
| GeoNetwork | ядро | ядро (CSW) | ядро (ссылки на сервисы и файлы) |
| OpenDataSoft, Socrata | ядро | ядро (выгрузка DCAT) | ядро (API к таблицам) |
| ArcGIS Hub | ядро | ядро (DCAT и OGC API Records) | ядро (слои и файлы) |
| PxWeb | ядро | нет | ядро (SDMX и JSON-stat) |
| JKAN, статический сайт | нет | ядро (файл `data.json`, если его собрали) | нет (ссылки на файлы) |

По выгрузке реестра dataportals-registry от 9 октября 2026 года (выпуск 1.26.0 от 6 октября) программный интерфейс отмечен примерно у двух третей каталогов. Чаще всего встречаются не «универсальные API», а то, что платформа отдаёт сама: sitemap, файл DCAT-US, интерфейс ArcGIS, RSS, OAI-PMH, каталог OGC, DCAT-AP, картографические сервисы WMS и WFS, API CKAN, сервис CSW. Поэтому картина интерфейсов повторяет картину платформ: много сайтов ArcGIS — много точек ArcGIS и DCAT.

## Как проверить живой портал

Документация для разработчиков на самом сайте — первый признак. Дальше проверьте типичные адреса. Подставьте домен портала:

```bash
# CKAN: поиск наборов
curl -s "https://portal.example/api/3/action/package_search?rows=1" | head

# Выгрузка описаний
curl -I https://portal.example/data.json

# Карта сайта
curl -I https://portal.example/sitemap.xml

# Научный репозиторий
curl -I "https://portal.example/oai?verb=Identify"

# Геопортал
curl -I "https://portal.example/csw?service=CSW&request=GetCapabilities"

# Неявные интерфейсы платформ
curl -s "https://portal.example/wp-json/" | head          # WordPress
curl -s "https://portal.example/server/api" | head        # DSpace 7 и новее
curl -s "https://gis.example/arcgis/rest/services?f=json" # сервер ArcGIS
curl -s -H "Accept: application/json" "https://portal.example/catalog?q=" | head  # Blacklight и другие
```

Хороший результат: ответ без входа в систему, в нём есть описания наборов, а не только главная страница. Плохой: капча, обязательная регистрация или поиск, который не умеет отдать следующую страницу.

Проверьте и полноту. Если поиск говорит, что наборов 10 000, а выгрузка содержит 200, сборщик увидит не тот каталог, который видит человек.
