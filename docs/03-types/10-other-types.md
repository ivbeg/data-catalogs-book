# Каталоги API, маркетплейсы и списки наборов

Три типа встречаются реже геопорталов и порталов открытых данных. Их легко не заметить в общей статистике и легко перепутать с «настоящим» порталом. У каждого ниже одинаковый короткий разбор: что это, стандарты, платформы, примеры, где ломается и когда такой каталог нужен.

Числа — по выгрузке реестра от 9 октября 2026 года (выпуск 1.26.0 от 6 октября).

## Каталоги API

**Что это.** Портал для разработчиков: список программных интерфейсов органа власти, транспортной компании или банка, с документацией и примерами запросов. В реестре около 115 таких каталогов, три четверти самописные.

**Стандарты.** Описание интерфейса — OpenAPI для обычных запросов и ответов, AsyncAPI для потоков событий. По описанию OpenAPI инструменты сами строят страницу документации и проверяют запросы. RFC 9727 (июнь 2025) задаёт стандартный адрес `/.well-known/api-catalog`, по которому программа находит список интерфейсов сайта, не зная заранее, где лежит портал разработчика.

**Платформы.** Портал разработчика из системы управления API: Azure API Management — частая основа в реестре, WSO2 API Manager — свободный вариант. Небольшой каталог — статический сайт, который собирают из файлов OpenAPI.

**Примеры.** [api.gov.uk](https://www.api.gov.uk) — каталог API британского правительства, [API-register Нидерландов](https://apis.developer.overheid.nl/), [APIs.guru](https://apis.guru/) — открытый сборник описаний OpenAPI для публичных интерфейсов.

**Где ломается.** Описание OpenAPI отстаёт от живого интерфейса: в документации одно поле, в ответе другое. Каталог перечисляет интерфейсы, для которых нужен ключ, но не говорит, как его получить и сколько ждать.

**Когда нужен.** Когда у организации много API и разработчику нужен один вход. Один API ведомства живёт на странице документации и в каталоге не нуждается. Это каталог данных только отчасти: он описывает сервисы, а не наборы. Если за API стоит набор данных, набор стоит описать и в обычном каталоге, со ссылкой на API как на способ получения.

## Маркетплейсы данных

**Что это.** Площадки, где данные продают или отдают по договору. В реестре около 55 записей, почти все самописные.

**Стандарты.** Общего стандарта описания товара нет, каждая площадка ведёт свою карточку. Там, где доступ договаривают между организациями, условия использования начинают описывать машиночитаемо: ODRL — язык W3C для правил вида «можно использовать для исследований, нельзя передавать третьим лицам». Его применяют европейские пространства данных вместе с описаниями наборов в DCAT.

**Платформы.** Крупные облачные площадки, где данные покупают и сразу получают в своё облачное хранилище: AWS Data Exchange, Snowflake Marketplace. Площадки-витрины поставщиков вроде Datarade. Открытые платформы каталогов почти не умеют брать оплату. Граница с порталами открытых данных размывается: в 2025 году OpenDataSoft переименовалась в Huwise и стала продавать ту же платформу как маркетплейс данных, в том числе для обмена внутри организации.

**Какие бывают.** Под одним словом «маркетплейс» живут четыре разные модели.

- **Государственные и отраслевые площадки.** data.europa.eu — общественная инфраструктура без платы. Шанхайская биржа данных проводит платные сделки между компаниями. Catena-X в автопроме совмещает некоммерческое управление с платными услугами подключения. Государство здесь ещё и продвигает площадку, и может быть регулятором, поэтому на ней появляются данные, которых нет больше нигде.
- **Данные внутри профессионального продукта.** Bloomberg и LSEG продают не наборы, а связку из данных, идентификаторов, лицензий и рабочего места трейдера. Это скорее способ встроить данные в продукт, чем отдельный рынок.
- **Площадки облачных провайдеров.** AWS, Snowflake, Google, Databricks. Они различаются тем, берут ли оплату сами и как доставляют данные. Общая логика одна: площадка увеличивает потребление основной облачной платформы.
- **Витрины поставщиков.** Datarade помогает найти поставщика и передать ему запрос, а договор, оплата и доставка остаются между сторонами. Это каталог с привлечением покупателей, а не биржа.

**Почему площадки редко взлетают.** Владельцам действительно востребованных данных посредник не нужен: клиенты и так приходят к ним на их условиях. Владельцы боятся, что посредник использует или перепродаст данные. А польза от «площадки» у данных меньше, чем у товаров: данные покупают редко, часто это разовая покупка или долгая подписка, и договариваться удобнее напрямую с поставщиком.

**Примеры.** [Datarade](https://datarade.ai/), [AWS Data Exchange](https://aws.amazon.com/data-exchange/), [Snowflake Marketplace](https://app.snowflake.com/marketplace), [Catena-X](https://catena-x.net/).

**Где ломается.** Описание товара закрыто до регистрации. Тогда покупатель не понимает, что покупает, а поисковик не видит, что данные существуют. Рабочая схема другая: описания открыты, оплата и выдача идут отдельной системой.

**Когда нужен.** Когда данные действительно продают и нужен договор на каждую выдачу. Если цель — открыть данные, маркетплейс лишний. Свою площадку для чужих данных строить почти никогда не стоит; почему — в [карточке решения](../06-choice/05-build-or-buy.md#пример-свой-маркетплейс-данных). Связка с европейскими пространствами данных, где доступ договаривают между организациями, разобрана в [главе о трендах](../11-trends/01-ai-and-data-spaces.md).

## Списки наборов

**Что это.** Страница, таблица или репозиторий со ссылками на файлы. В реестре около 110 таких списков. Программный интерфейс есть примерно у 13%.

**Стандарты.** Чаще никаких. Довести список до машиночитаемого вида помогают разметка schema.org/Dataset на странице и файл `datapackage.json` рядом с данными.

**Платформы.** Обычная веб-страница, файл README в Git-репозитории, общая таблица.

**Примеры.** [awesome-public-datasets](https://github.com/awesomedata/awesome-public-datasets) — тематический список открытых наборов на GitHub, который ведёт сообщество. [Registry of Open Data on AWS](https://registry.opendata.aws/) — список наборов, лежащих в облачном хранилище, собранный из файлов описаний в репозитории.

**Где ломается.** Ссылки умирают, и никто это не проверяет. У наборов нет лицензии и даты. Список дублирует чужие каталоги и устаревает быстрее них.

**Когда нужен.** Список — нормальный способ опубликовать десяток наборов. Он становится тупиком, когда нет лицензии, постоянных адресов и разметки. Как довести список до находимой публикации, написано в части [«Публикация без портала»](../08-beyond-portals/01-when-portal-not-needed.md). Заводить ради такого списка CKAN не нужно.
