# Git-репозитории

Репозиторий хранит данные вместе с описанием и, если нужно, со скриптом, который данные собирает. Видна история: кто что поменял и когда. Для таблицы, которую ведут несколько человек, это часто удобнее формы на портале.

Площадки — GitHub, GitLab и другие. Правила размера у них разные; ниже ориентир GitHub на 2026 год, перед публикацией большого файла сверьтесь с текущей документацией площадки.

## Огромный архив, который трудно искать

GitHub, возможно, крупнейшее в мире хранилище файлов с данными: уже в 2022 году поиск по имени файла находил на нём десятки миллионов CSV, JSON, XML и баз SQLite. Каталогом он от этого не становится. У репозитория нет признака «здесь данные»: для площадки он такой же, как репозиторий с кодом. Поиск по содержимому файлов работает только после входа в учётную запись и метаданных набора не знает. Темы (topics) автор ставит по желанию: на 12 октября 2026 года тему `dataset` указали около 19,5 тысячи репозиториев, `open-data` — около 10,4 тысячи, а это ничтожная доля от общего числа.

Поэтому человек и поисковик данных отличают репозиторий с данными от репозитория с кодом только по косвенным признакам: что написано в `README.md`, какие файлы лежат в корне, есть ли `datapackage.json`. Наборы на GitHub в 2024 году приходилось искать именно так — запросом по файлам `datapackage.json`. Отсюда практический вывод: то, что ниже названо обязательным, нужно не только пользователю, но и находимости. Добавьте ещё темы `dataset` и `open-data` — это бесплатно и помогает тем, кто ищет данные по темам.

## Что положить в репозиторий

Готовые файлы лежат в [шаблонах](pathname:///templates/README.md). Скопируйте и замените примеры своими.

| Файл | Зачем |
|------|--------|
| `README.md` | что это, за какой период, как обновляется, кто отвечает |
| `LICENSE` | лицензия именно на данные |
| `datapackage.json` | имена колонок и их смысл по правилам Frictionless Data Package |
| `data/` | сами файлы в открытых форматах: CSV, JSON, Parquet |
| `CITATION.cff` | как сослаться; GitHub показывает это как кнопку цитирования |

Если данные собираются скриптом, скрипт тоже лежит в репозитории, а обновление запускается автоматически (на GitHub это Actions). Тогда «забыли обновить таблицу» видно по упавшему запуску, а не по молчанию сайта.

## Выпуск и DOI

Метка версии (тег) фиксирует состояние, на которое можно сослаться. Связка GitHub и Zenodo умеет забирать каждый выпуск и выдавать ему DOI. Пока связки нет, уберите из шаблона `CITATION.cff` блок с пустым DOI, чтобы не цитировать несуществующий номер.

DOI нужен, если на эти данные будут ссылаться в тексте. Для внутренней таблицы организации он не обязателен.

## Форматы под тех, кто будет пользоваться

В репозитории легко выложить сразу несколько форматов, и это заметно влияет на то, возьмут ли данные. Пример — два репозитория со списком стран и их кодами. [Country Codes](https://github.com/datasets/country-codes) аккуратно сделан: CSV, описание колонок в `datapackage.json`, скрипт сборки. [Country List](https://github.com/umpirsky/country-list) даёт тот же список на всех языках и в одиннадцати форматах: CSV, JSON, YAML, XML, HTML, готовые SQL-файлы для MySQL, PostgreSQL и SQLite, PHP и другие. У первого на октябрь 2026 года около 980 звёзд на GitHub, у второго — около 5,3 тысячи. Разработчику проще взять файл, который сразу загружается в его базу или программу, чем преобразовывать CSV.

Вывод не в том, что описание колонок не нужно. Его нужно дополнить форматами, в которых данными пользуются. Сначала выясните, кто эти люди: аналитик ждёт CSV или Parquet, разработчик — JSON или SQL, переводчик — файл локализации.

## Код сборки вместо данных

Иногда выгоднее опубликовать не таблицу, а программу, которая её собирает. Так поступают, когда первоисточник выкладывает данные в Excel, меняет файлы без предупреждения или не даёт на них прямой ссылки. Готовая таблица устареет при следующем обновлении источника, а скрипт любой может запустить заново и получить свежую версию. В 2022 году так были опубликованы, например, сборщики реестров аккредитованных ИТ-компаний и отечественного ПО с сайта Минцифры России: в [репозитории](https://github.com/apicrafter/datacrafter-examples) лежат не данные, а описания того, откуда и как их брать.

Слабое место у такого способа одно: скрипт живёт, пока жив источник. Если ведомство уберёт файл или сменит сайт, код станет бесполезен, а данных у вас не останется. Поэтому код сборки дополняют результатом: выпуском с готовыми файлами в том же репозитории или копией в Zenodo. Как сохранять данные, которые могут исчезнуть у источника, — в главе [об архивации](../09-practices/04-archiving.md).

## Пределы

- На GitHub файл больше 100 МБ в Git не кладут. Большие файлы — через Git LFS, вложения к выпуску или отдельное хранилище, а в репозитории остаётся описание и адрес файла. Git LFS — дополнение к Git, которое хранит большие файлы отдельно, а в истории оставляет только ссылки на них. Так устроен [geoBoundaries](https://github.com/wmgeolab/geoBoundaries): границы административных единиц всех стран, все выпуски лежат в LFS, лицензия CC BY 4.0, рядом сайт и API.
- Площадка может сменить правила или стать неудобной в вашей стране. Копия выпуска в Zenodo или другом архиве эту зависимость уменьшает.
- Сам по себе репозиторий поисковики данных почти не видят. Нужна страница с разметкой schema.org: сайт на GitHub Pages из тех же файлов или запись в чужом каталоге.

## Как не превратить репозиторий в свалку

Один набор — один репозиторий или одна понятная папка с собственным `datapackage.json`. Десять несвязанных таблиц в одном репозитории без описания колонок — это та же «простыня ссылок», только в Git.

Сквозной порядок от репозитория до находимости — в главе [«Как сделать публикацию находимой»](./05-making-it-findable.md).
